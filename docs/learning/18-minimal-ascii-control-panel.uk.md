# Мінімальна ASCII-панель OnboardAutonomy

## Що змінилось

Попередній TUI був схожий на діагностичний лог: він показував сім останніх
MAVLink-подій, часові мітки, напрямки `TX/RX` і багато паралельних статусів.
Дані були правильними, але головна ідея губилась.

Новий екран показує систему, а не журнал:

```text
+--o--------------o--+                MAVLINK                 /--o--------------o--\
|   RASPBERRY PI 5   |--[ TAKEOFF: 5.0 M ]------------------->|     PIXHAWK 6C      |
| COMPANION COMPUTER |<-----------------[ TAKEOFF: ACCEPTED ]-| FLIGHT CONTROLLER  |
|    HEARTBEAT ON    |                                        |   GUIDED / ARMED   |
+--o--------------o--+                                        \--o--------------o--/
```

Зліва працює конкретний companion computer `Raspberry Pi 5`. Справа працює
цільовий flight controller `Pixhawk 6C`. Верхній
провід показує останню корисну команду, нижній - останню відповідь або зміну
стану контролера.

`HEARTBEAT ON` означає, що companion регулярно надсилає службове MAVLink
повідомлення "я живий". `DISARMED` означає, що контролер блокує моторні виходи,
а `ARMED` - що контролер дозволив їх. У симуляції це стан контролера, а не
твердження, що фізичні мотори обертаються.

## Кольори

Колір тепер групує інформацію за її власником або призначенням, а не фарбує
весь рядок одним статусом:

- cyan: `Raspberry Pi 5`, OnboardAutonomy і команди від companion;
- yellow: `Pixhawk 6C`, ArduPilot, телеметрія та відповіді контролера;
- green: успішний загальний стан, наприклад `ONLINE` або `READY`;
- red: помилка команди чи неготовність;
- blue: зовнішня рамка інтерфейсу;
- white: нейтральні flight data та клавіші керування;
- gray: дані, які ще очікуються або неактивні.

Для warning yellow має вищий пріоритет, а для failure red має вищий пріоритет
за колір джерела повідомлення.

## Що навмисно приховано

`SET_MESSAGE_INTERVAL` потрібна для налаштування частоти телеметрії, але це
службова операція. Вона залишається в `AppSnapshot.link_events`, проте
`ConsoleView` не показує її на основній панелі.

Так само більше немає:

- семи рядків історії подій;
- часових міток;
- написів `TX` і `RX`;
- повторення одного стану в кількох секціях.

Історія не видалена з application-шару. Пізніше її можна записати у файл або
показати в окремому debug-режимі без змін польотної логіки.

## Межа відповідальності

Змінено тільки:

```text
src/presentation/console/ConsoleView.cpp
tests/ConsoleViewTests.cpp
```

`CompanionApplication` досі збирає семантичні `LinkEvent`. MAVLink decoder,
command encoder, automated flight controller і safety policy не змінювались.

Це важлива архітектурна властивість: presentation вирішує, **як показати**
стан, але не вирішує, **що відправляти дрону**.

## Цікаві місця C++

Останню корисну подію шукаємо з кінця:

```cpp
const auto match = std::find_if(
    events.rbegin(),
    events.rend(),
    [direction](const LinkEvent& event) {
        return event.direction == direction &&
               !is_internal_setup_event(event);
    }
);
```

`rbegin()` і `rend()` створюють reverse iterators. Завдяки цьому перший
знайдений елемент є найновішим, а не найстарішим.

Лямбда `[direction]` захоплює значення напрямку. Вона працює як локальний
predicate для `std::find_if`.

Рядки пристроїв збираються з колонок фіксованої ширини:

```cpp
return " " +
       fitted(companion, kDeviceWidth) +
       fitted(link, kLinkWidth) +
       fitted(controller, kDeviceWidth) +
       " ";
```

Тому довга команда обрізається всередині свого проводу й не ламає зовнішню
рамку. Це не бізнес-логіка, а інваріант presentation-шару.

## Що лишилось на екрані

- стан MAVLink-з'єднання;
- два ASCII-пристрої та напрямок обміну;
- остання команда і відповідь;
- mode, altitude, GPS і battery;
- одна активна warning замість журналу;
- стан сценарію та клавіші `[1]`, `[L]`, `[Q]`.
